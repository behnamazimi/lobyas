# Finding 15: Pre-redesign assets and colors remain (PWA screenshots, theme color, emails)

**Severity:** medium | **Category:** legacy assets

## Summary

The install screenshots in the web manifest show the old app, and the manifest and email colors don't match the current palette.

## Where it shows

- `public/screenshots/` (`read-narrow.png`, `read-wide.png`, `review-*.png`, `quiz-*.png`), referenced from `app/manifest.ts` (`PWA_SCREENSHOT_WIDE`, `PWA_SCREENSHOT_NARROW` in `lib/pwa.ts`); last changed Oct 11, before the redesign.
- `lib/pwa.ts`: `PWA_THEME_COLOR = "#3f4755"`, `PWA_BACKGROUND_COLOR = "#fdfcf9"`; `<meta name="theme-color">` renders #3f4755.
- `lib/email/resend.ts` and `lib/requests/email-copy.ts`: inline styles `background:#111`, `color:#666`, 6 px radius, no brand font.

## What is wrong

- The screenshots show the old header (logo, avatar), the "All active collections (20)" selector, the old five-tab bar and a green "Next term" button, none of which exists now (`docs/redesign.md` dropped "All active collections" and the five tabs).
- Palette: page background is `#f7f4ee` (`base-200`) in light and `#27221e` in dim; ink is `#2a2420`. The manifest's `#3f4755` (a blue-gray) and `#fdfcf9` are in neither theme, so the browser chrome and splash screen don't match the app.
- Emails are a neutral black button on white, unrelated to the app's ink, cream or fonts.

## What it conflicts with

- `app/globals.css` theme tokens (light and dim).
- Store listing and install UI show these screenshots, so the old UI is what a new person sees before installing.

## Where to look in the code

- `public/screenshots/`, `lib/pwa.ts`, `app/manifest.ts`, `app/layout.tsx` (theme-color meta), `app/splash/`, `app/icon.tsx`, `app/apple-icon.tsx`
- `lib/email/resend.ts`, `lib/requests/email-copy.ts` (+ `email-copy.test.ts`)
- `docs/mobile.md` (store screenshots) before touching native assets

## Reproduce

1. Open `public/screenshots/read-narrow.png` and compare it with `/app/read` at 390×844.
2. `curl -s http://localhost:3000/manifest.webmanifest` and read the theme and background colors.
3. View the page source of `/login` and read `theme-color`.

## Evidence

No screenshot; the evidence is measured values (see "What is wrong").

## Also affects

Finding 16 (dark theme: the theme-color meta isn't theme aware).

## Questions the fixer should answer

- Are the screenshots generated by a script (is there one in `scripts/`)? If not, how should they be refreshed?
- Should `theme-color` follow the theme (light and dim)?
- Do emails need the app's look, or stay plain on purpose?

## Done when

- Install screenshots match the current UI.
- `theme-color` and manifest `background_color` correspond to the app's own colors.
- Email styling is a conscious choice, documented.

## Ground rules for the fixer

- Read `AGENTS.md` and the docs it links for the area you touch (`docs/redesign.md` for the design decisions, `docs/e2e.md` before adding a spec). Where `docs/redesign.md` and the canvas disagree, the decision in the doc wins.
- Build from the shared kit (`components/kit/`) and DaisyUI classes with theme tokens from `app/globals.css`. No new hard-coded hex colors in components.
- Restyle only. Don't change server actions, routes, RPCs or TRACE. Keep `data-tour` attributes, `saveInBackground` usage and the term-layout portal rules intact.
- Keep tap targets at least 44 px on phone and text contrast at least 4.5:1 in light and dim (dark) themes.
- Comments only where necessary, in plain language.
- Finish with `pnpm check`; run `pnpm test:e2e:smoke` if a covered flow changes.
- Don't take the "Conflicts with" or "Questions" sections as the answer. They state the problem and what a solution has to respect. Choose the solution yourself; if it changes one of the shared pieces named here, check the other pages that use it (the "Also affects" list).
